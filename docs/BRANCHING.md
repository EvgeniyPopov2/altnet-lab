# BRANCHING.md — стратегия веток, релизов и деплоя

## Ветки
- **main** — стабильная. Содержит только проверенное. Попадание в main — через PR из `lab` (релиз) или из `hotfix/*`.
- **lab** — текущее состояние Vagrant-стенда. Сюда мерджим из `dev`, после чего накатываем на узлы.
- **dev** — активная разработка. От неё ответвляем короткоживущие ветки `feature/*`.

Доп. ветки по ситуации:
- **feature/<кратко>** — задача/эксперимент; основа — `dev`.
- **hotfix/<версия>** — срочное исправление от `main`, потом переносим изменения в `dev`/`lab`.

## Типовой цикл
1. От `dev` создаём `feature/xxx`.
2. Коммитим небольшими шагами (сообщения — по-русски, понятно что и зачем).
3. Открываем PR в `dev` → после ревью мерж.
4. Готово к стенду? PR `dev` → `lab`, мерж.
5. Деплой на узлы: на нодах обновляемся из `lab` и запускаем `scripts/altnet-apply.sh`.
6. Готовим релиз: PR `lab` → `main`, ставим тег `vX.Y.Z`, оформляем GitHub Release.

## UI-ветки: как не потеряться
- `ui/chat-mvp-clean` — историческая «чистая» ветка для промежуточной стабилизации UI перед merge в `ui/chat-mvp`.
- `ui/chat-mvp` — агрегирующая UI-ветка (в неё уже вливали `ui/chat-mvp-clean`).
- Для новых задач не плодим долгоживущие UI-ветки без необходимости: предпочитаем `feature/*` от `dev` и PR обратно в `dev`.

Практика для текущего репозитория:
1. Проверяем, в какой ветке стоим: `git branch --show-current`.
2. Перед началом работы обновляем удалённые ссылки: `git fetch origin --prune`.
3. Сравниваем локальную ветку с целевой на GitHub: `git log --oneline --left-right --cherry-pick origin/<target>...<local>`.
4. Если задача UI и нужна отдельная ветка — создаём короткоживущую `feature/ui-<task>` от `dev`.
5. После merge ветку удаляем, чтобы снова не копить «непонятные» параллельные потоки.

## Hotfix
1. От `main`: `hotfix/vX.Y.Z+1`.
2. Исправляем → PR в `main` → тег `vX.Y.Z+1`.
3. Переносим фиксы в `dev` и при необходимости в `lab` (cherry-pick/merge).

## Версионирование и релизы
- Семантическое (`MAJOR.MINOR.PATCH`), теги вида `v0.1.0`.
- Релизы оформляем на GitHub; бинарные артефакты приложений добавим позже (CI).

## Структура каталога (кратко)
- `systemd/`, `etc-default/`, `tor/`, `scripts/`, `srv/` — инфраструктура стенда.
- `src/` — исходники сервисов (например, `src/discovery/`).
- `apps/` — будущие клиенты: `apps/desktop/`, `apps/android/`, `apps/linux/`, `apps/ios/`.
- `docs/`, `inventory/`, `vagrant/` — документация, описание узлов, Vagrant.

## Секреты и чувствительные данные
- В Git только `*.example`. Живые файлы игнорируем (см. `.gitignore`).
- Перенос секретов на узлы — вручную/через Ansible позже.

## Деплой на Vagrant-стенд (ручной, пока)
- Ветка: `lab`.
- На узле: `git pull` (или обновление синхронной папки) → `sudo bash /home/vagrant/altnet_repo/scripts/altnet-apply.sh`.

## Платформы
- Платформы — папками в `apps/*`, а не отдельными ветками.
- Сборочные пайплайны настроим позже (матрица CI по ОС/арх.).

## Сообщения коммитов (рекомендуемый стиль)
- Коротко и по делу: `systemd: обновить discovery@.service — добавить TOR_PREFIX`
- `docs: дополнить README — раздел про sync`
