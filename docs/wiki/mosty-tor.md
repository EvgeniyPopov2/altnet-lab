# Мосты Tor в отдельной копии AltNet

Каждая установка содержит собственный клиент Tor, каталог, настройки и интерфейс. Для работы достаточно одной копии. Виртуальные машины node1, node2 и node3 служат испытательным стендом.

## Запуск

В поставке для x86-64 откройте `AltNet.cmd` на Windows или выполните `./Start-AltNet.sh` в распакованном каталоге на Linux. Понадобятся Python 3.10+ и gpgv. В Windows запускающий скрипт также находит gpgv из Git for Windows. Независимый каталог для первой загрузки, публичный ключ и Tor Expert Bundle включены в поставку.

Откройте `http://127.0.0.1:17860` и нажмите **Мосты Tor**. Индикатор показывает построение цепочки и автоматическое восстановление. В окне видны доступность источника, прогресс загрузки Tor и результат отдельного HTTPS-запроса. Кнопка **Обновить список** проверяет каталог. **Сменить мост** исключает действующие входные узлы из новой пробы. Кнопка **Добавить и проверить** принимает до 16 строк obfs4, в том числе с префиксом `Bridge`. Строки ложатся в личный список после подтверждения рабочей цепочки. Во время посылки нескольких мостов сразу подтверждается тот вход, через который построена цепочка.

Приложение может использовать SOCKS5h на `127.0.0.1:17861` с разрешением имени через Tor. Пока подтверждённого маршрута нет, локальный порт закрывает клиентское соединение. При смене маршрута новые подключения используют проверенную цепочку. Старым потокам даётся до 30 секунд на завершение. Сетевые функции остальных экранов AltNet требуют собственной интеграции с этим портом.

## Восстановление

Клиент сначала перепроверяет подпись локального архива. При наличии последнего успешного входа он пробует его, затем остальные сохранённые мосты. После построения цепочки проверяет стабильную поставку на сайте Tor Project через Tor. При потере цепочки исключает только что отказавшие входы из первой резервной пробы. Входы возвращаются в рассмотрение при последующих попытках. Проверка кандидата проходит в отдельном процессе Tor. Для подтверждения нужны 100% bootstrap, построенная цепочка GENERAL или CONFLUX_LINKED, известный первый переход и рабочий локальный SOCKS-слушатель. При исчерпании obfs4 клиент с установленным транспортом пробует параметры Snowflake из подписанной поставки.

Если Tor перестал продвигаться, через 85 секунд клиент освобождает попытку. При пяти повторных сетевых ошибках obfs4 в начале загрузки клиент переходит к резерву уже после 25 секунд. Общий предел одной пробы составляет 180 секунд. Интервал повторов с разбросом растёт от 5 секунд примерно до 5 минут. Успешный каталог проверяется снова через сутки, при потере источника опрос повторяется примерно через три минуты. Ручной запрос запускает внеочередную проверку. После двух подряд неудачных проверок HTTPS через действующий Tor клиент пробует резерв, сохраняя прежнее соединение до результата. Успешный ответ Tor Project с `IsTor=true` показывается отдельно от готовности цепочки.

При недоступном Tor клиент использует локальную подписанную поставку и кэш. Запрос официального каталога выполняется через подтверждённый SOCKS Tor. Если маршрута нет, обновление ожидает восстановления связи. Прямой запрос к сайту, локальный поиск соседей и раздача каталога выключены до реализации и проверки сетевых профилей. Публичный каталог проверяется по подписи и защите от отката. Личные мосты остаются в локальном хранилище.

## Параллельный поиск и питание

Клиент начинает с одной группы. Если связь ещё не установлена и загрузка остаётся ниже 80% без продвижения 12 секунд, он может запустить вторую независимую проверку. Она пробует другой транспорт или другие адреса. Первый подтверждённый маршрут остаётся активным, второй процесс завершается. При наличии рабочей цепочки автоматический поиск в фоне прекращается. Ручная проверка замены сохраняет действующую цепочку до результата.

Две параллельные пробы разрешены при внешнем питании и загрузке процессора ниже 75%. На батарее, при энергосбережении, высокой нагрузке или неизвестном состоянии питания разрешена одна. Если питание меняется во время двух проб, сохраняется более продвинутая. Сведения о питании и общей загрузке считываются с интервалом не менее восьми секунд. При установленной связи проверка локального состояния выполняется примерно каждые 8–16 секунд. Опрос скрытой вкладки замедляется.

Для постоянного ограничения одной пробой укажите `"parallelProbes": 1` в `network.json` на Windows или добавьте `--parallel-probes 1` на Linux. В окне «Мосты Tor» во время поиска видны фактическое число проверок и текущий лимит.

За 100 секунд поиска на Windows с 12 логическими процессорами одна проба в среднем занимала 0,062% общей мощности CPU, две — 0,127%. В однородных интервалах длительностью 25,4 и 71,8 секунды соответственно пик частной выделенной памяти процессов клиента составил 85,6 и 140,3 МиБ. Измерены клиент, Tor и транспорт. Браузер в измерение не входит. В отдельной двухпроцессорной ВМ Ubuntu установленная цепочка Snowflake с нулём поисковых проб за 50,1 секунды потребила 1,61 процессорной секунды. Продолжительность работы ноутбука от батареи требует измерения на конкретном устройстве.

## Обмен с соседями

Получение и раздача каталогов соседям ожидают интеграции с сетевыми профилями. Параметры старой установки `peers`, `shareOn` и локальное обнаружение не запускают сетевой обмен. Подтверждённая цепочка Tor используется для запроса официального источника. Пользователь может вручную добавить мост через окно «Мосты Tor». [Официальные способы получить мост](https://support.torproject.org/tor-browser/circumvention/getting-bridges/)

## Что проверено 23 ноября 2026 года

На трёх Ubuntu исправлены права AppArmor на чтение включаемых конфигураций Tor. Из четырёх исходных мостов три отказали в TCP-соединении, один не ответил с node1. После добавления публичных мостов из подписанной поставки на каждом узле проверены цепочка и реальный HTTPS-ответ Tor Project через SOCKS.

В испытании с принудительным обрывом двух действующих мостов отдельная установка восстановила цепочку через другой вход за 14,1 секунды. Когда перекрыты все достижимые варианты, получение того же каталога не создаёт маршрут. Для отказа сайта проверена доставка между двумя независимыми хранилищами и отбраковка повреждённой подписи. При повторных обрывах новый вход был подтверждён за 43 и 246 секунд, через оба прошёл реальный HTTPS-запрос. Ранее отдельно проверялся multicast-обмен каталогом. Этот эксперимент отключён, пока не реализованы сетевые профили. На Windows подтверждён выход через obfs4, на Linux также проверен Snowflake. Это измерения на стенде с общим выходом, испытания у разных проводных и мобильных провайдеров остаются отдельной задачей.

Поддержка ручного WebTunnel и измерения доступности по каждому провайдеру остаются в плане. Строгий белый список может закрыть и входной мост, и посредников всех доступных транспортов. В этом случае интерфейс показывает ожидание следующей попытки и допускает ручной импорт.
