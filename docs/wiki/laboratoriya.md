# Лаборатория AltNet

Лаборатория нужна для проверки связи между отдельными узлами. Это испытательный стенд, а не работающая анонимная сеть приложения.

## Проверка после обновления 23 ноября 2026

Все три узла прошли обновление пакетов Ubuntu 22.04 и перезагрузку. На каждом загружено ядро `6.8.0-149-generic`, установлен метапакет HWE, `dpkg --audit` пуст, APT не предлагает дальнейших обновлений по обновлённому индексу. SSH, API IPFS, управление Yggdrasil и монтирование `/vagrant` проверены из работающих систем. До обновления для каждой выключенной ВМ создан снимок `pre-ubuntu-altnet-20261123` на диске H.

AppArmor разрешает профилю `system_tor` чтение каталога включаемых конфигураций и файлов `*.conf`. Экземпляр `tor@default` работает с применённым профилем. После дополнения исходного списка публичными мостами подписанной поставки все три узла достигли 100% bootstrap. Контрольный тест подтвердил цепочки с первыми переходами через настроенные мосты. [Испытания и проект управления мостами](mosty-tor.md).

На `node2` регистрировалось 246 запусков `altnet-apply` за минуту. Неудачная попытка применения `demo/1.0.0` оставляла активный маркер `.fetched`. Теперь обработчик забирает событие до проверки архива, а повторная публикация создаёт новое событие. На каждом узле проверено 65 секунд простоя очереди после перезагрузки. [Регрессионные тесты](../TESTS.md).

## Исходное состояние до этих исправлений

23 ноября 2026 года найдены три сохранённые виртуальные машины `node1`, `node2` и `node3`. Их идентификаторы совпали с данными старой конфигурации Vagrant, SSH-отпечатки всех трёх сверены с консолями машин. До обновления на всех узлах работали Ubuntu 22.04.5 и ядро `5.15.0-161-generic`.

| Узел | Состояние ядра и доступа |
|---|---|
| `node1` | Установлено и загружено `6.8.0-149-generic`; SSH, IPFS и Yggdrasil после перезагрузки доступны. |
| `node2` | Пакет `6.8.0-149-generic` установлен, файлы старого ядра сохранены; после перезагрузки SSH пока не ответил. Фактически загруженное ядро и состояние сервисов нужно проверить в консоли. |
| `node3` | Работало прежнее ядро `5.15.0-161-generic`; обновление отложено до восстановления `node2`. |

Снимок или полноценная резервная копия перед обновлением ядер не подтверждены. Предыдущее ядро оставлено, но это не заменяет резервную копию. На `node1` после обновления списков пакетов оставались ещё 242 пакета с доступными обновлениями; это не означает, что все они обновления безопасности. На `node2` такая же цифра наблюдалась перед установкой ядра; для `node3` актуальный список ещё не обновлён.

| Проверка `node1` | Результат |
|---|---|
| SSH | Подключение работает после сверки отпечатка непосредственно в консоли виртуальной машины. |
| Yggdrasil | Служба запущена. Политики маршрутизации и изоляция не проверены. |
| IPFS | До обновления на трёх узлах Kubo `0.29.0` работал от пользователя `vagrant`; в текущих хранилищах ключ приватного роя отсутствовал. На `node1` служба запустилась после обновления ядра. |
| Обнаружение IPFS | В конфигурации указан `Routing.Type = none`, но обнаружение через mDNS включено. Это наблюдение по настройкам, а не результат испытания на отсутствие утечек. |
| Подключения IPFS | На момент проверки обнаружены три подключения: два к неглобальным адресам и одно к адресу из диапазона Yggdrasil. По этим сведениям нельзя установить личности участников или подтвердить полную изоляцию. |
| Tor | При запуске `tor@default` завершился с ошибкой чтения включения `/etc/tor/torrc.d/*.conf`. Сейчас в каталоге видны два файла, а отдельная проверка конфигурации от пользователя Tor проходит. Причина ошибки при загрузке пока не установлена; служба не перезапускалась. Статус обёртки `tor` не подтверждает работу экземпляра. |

Наличие файла `swarm.key` в старой папке на компьютере само по себе не означает, что он используется работающим IPFS внутри виртуальной машины. До обновления ядра конфигурации IPFS, Tor и Yggdrasil не менялись; обновление ядра и перезагрузка `node1` и `node2` изменили состояние этих систем.

## Что предстоит сделать

1. Проверить экран `node2`, восстановить SSH и удостовериться, что оно загружено на новом ядре; только после этого продолжить обновление `node3`.
2. Определить существующие подключения, настройки обнаружения и маршрутизацию. Не использовать личные данные для испытаний, пока изоляция не подтверждена.
3. Подготовить и проверить вариант изолированной лаборатории с понятным откатом, затем согласовать его с фактической конфигурацией узлов.
4. Исправить и проверить Tor как отдельную задачу; запуск службы сам по себе не доказывает анонимность приложения.
5. После настройки провести проверку обмена тестовыми данными между узлами и отдельно проверить отсутствие нежелательных внешних соединений.

Не публикуйте секретные ключи и полные конфигурации узлов. Для сверки SSH подходит только публичный отпечаток, полученный в консоли соответствующей виртуальной машины.
